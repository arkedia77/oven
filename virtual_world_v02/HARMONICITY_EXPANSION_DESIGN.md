# 하모니시티 확대 설계 (Expansion Design v1.0)

작성: oven, 2026-07-07
성격: 기술 설계 문서. 사업 의사결정(가격/계약/우선순위 확정)은 venture-studio + Leo 결재 사항.
정합성 기준: Leo 확정 A트랙(B2B 학술 SaaS + 교육 시민 시뮬레이션, 게임 B트랙 제외),
"하모니시티는 게임이 아님 — 목표 달성이 아닌 **변화 관찰**이 핵심" 원칙.

---

## 0. 전제 — 지금 가진 것 (전부 실측 기반)

| 자산 | 상태 | 실측 근거 |
|------|------|----------|
| 도메인-애그노스틱 엔진 | ✅ | 5파일 교체로 도메인 전환, 엔진 코드 변경 0줄 (기업/교육/소비자 3종 검증) |
| 재현성 인프라 ①②③④ | ✅ | 시드고정 + LLM record/replay 비트단위 재현 + N=30 다회통계(CI ±0.004) + 논문포맷 export |
| 동시성 | ✅ | 단일 5090에서 N≤12 세계 실시간 SLA 유지, throughput 포화 N≈4 (4슬롯) |
| 운영 인프라 | ✅ | watchdog 자동복구 + 데일리백업 + dir-scoped 인스턴스 락(멀티테넌트 격리 기초) |
| 관계/평판/정보/욕구 7대 시스템 | ✅ | 11명 280일+ 무인 가동, Ceiling/포화 0 유지 (P2 항상성 패치 검증) |
| 비용 구조 | ✅ | 세계 1개 = GPU 월 ~1시간, 저장 ~30MB (10명 기준). 틱 활용률 4.2% |

핵심 판단: **엔진의 과학적 기반(재현성·항상성·도메인 독립)은 완성 단계**다.
확대의 병목은 시뮬레이션 품질이 아니라 **① 외부에서 쓸 수 있는 인터페이스가 없다**(Python 모노리식,
API 0개), **② 개입→결과를 비교하는 실험 프레임이 없다**(관찰만 가능, 통제 비교 불가),
**③ 장기 서사가 없다**(에피소드 기억 롤링 50건, 플롯 추적 없음) 세 가지다.
확대 설계는 이 세 병목을 푸는 순서로 구성한다.

## 1. 하모니시티 자체 확대 — 6개 축

### E1. 관측·개입 API 계층 (최우선 — 모든 응용의 관문)

현재 엔진은 JSON 파일로만 상태를 내놓는다. 응용 서비스가 되려면 세계를 "읽고 찌를 수 있는"
표준 인터페이스가 필요하다. 엔진 수정 최소화 — save/load가 이미 JSON이므로 얇은 REST 래퍼로 시작.

**관측 (read-only, 라이브 세계에 무해)**
- `GET /worlds/{id}/state` — day/tick/이벤트
- `GET /worlds/{id}/relationships` — 4축(warmth/trust/tension/affection) 행렬 + 시계열
- `GET /worlds/{id}/characters/{cid}` — needs/beliefs/goals/emotional_state
- `GET /worlds/{id}/reputation` — 관찰자별 평판 행렬 (정보 비대칭 뷰)
- `GET /worlds/{id}/conversations?since=` — 대화 로그 스트림
- `GET /worlds/{id}/metrics` — 다회통계에서 쓰는 표준 메트릭 8종 (avg_warmth 등)
- WebSocket/SSE 이벤트 피드 — 대시보드·수업용 실시간 관전

**개입 (write, 실험의 재료)**
- `POST /worlds/{id}/events` — 외부 이벤트 주입 (기존 event injection 경로 재사용)
- `POST /worlds/{id}/characters` — 캐릭터 투입 (ji_woo 자동통합 `_integrate_new_characters` 경로가 이미 있음)
- `PATCH /worlds/{id}/config` — 파라미터 조정 (감쇠율, 예산 등 — "조정값을 배우는" 원칙과 직결)
- `POST /worlds` / `DELETE` — 세계 라이프사이클 (E5와 연동)

구현 노트: FastAPI 단일 프로세스, 틱 사이 저장 시점의 스냅샷만 서빙(진행 중 틱의 불완전
상태 노출 방지 — 탐색에서 확인된 틱 동기화 제약). 기존 dashboard.py를 이 API의 첫 소비자로 이관.
예상 규모: 신규 코드만, 엔진 침습 거의 0. 라이브 무영향 원칙(재현성 트랙과 동일 방식) 유지.

### E2. 개입 실험 프레임 (재현성 자산의 상업적 완성형)

지금은 "한 세계를 관찰"만 가능하다. B2B의 실제 질문은 항상 **"이 개입을 하면 뭐가 달라지나"**다.
재현성 ①~④가 이미 있으므로, 남은 것은 이를 **통제 비교**로 조립하는 것뿐이다:

```
동일 seed로 세계 A/B 분기 → A는 baseline, B에만 개입(이벤트/캐릭터/파라미터) 주입
→ N시드 × 2조건 다회통계 → 조건 간 메트릭 차이 mean±std+95%CI → "개입 효과" 추정치
```

- `run_reproducible.py`의 `orchestrate_multiseed`를 2조건 비교(`orchestrate_ab`)로 확장 —
  `_extract_metrics`/`_stats`/export 전부 재사용. 신규 개발량이 작다.
- 동시성 실측(N≤12)이 여기서 바로 현금화됨: N=5시드 × 2조건 = 10세계 동시 = 1대 5090으로
  하나의 실험을 한 번에 처리.
- 산출물: "개입 X → tension –0.03±0.01 (95%CI), warmth 유의차 없음" 형태의 효과 리포트.
  이것이 S1(조직), S2(연구), S3(교육) 전부의 핵심 산출물 포맷이 된다.
- 원칙 정합: 목표 달성 판정이 아니라 **변화 추이의 조건 간 비교** — "게임 아님" 원칙 그대로.

### E3. 장기 기억·서사 계층

현재 한계(탐색 확인): 에피소드 기억 롤링 50건, 플롯/서사 추적 없음, 대화 간 연속성은
관계 수치로만 전달. 장기 구독형 서비스(연구·교육 모두 주 단위 이상 관찰)에는 서사 연속성이 품질을 좌우.

- **L2.5 요약 기억**: 롤링으로 버려지는 에피소드를 버리기 전에 주기 요약(10일 회고 인프라 재사용)
  → salience 높은 사건만 장기 보존. LLM 호출 증가는 회고 주기에만 발생(틱당 비용 불변).
- **플롯 스레드 추적**: "aria의 비밀 발각 진행도" 같은 다자간 사건 궤적을 명시 객체로.
  기존 information.py(비밀/소문/truth_value)가 이미 데이터를 갖고 있음 — 소문 전파 그래프를
  스레드 단위로 묶는 집계 계층만 추가.
- **네트워크 건강 모니터 (Phase12 후보)**: 관계 그래프 지표(고립 노드, 클러스터화, 긴장 집중도)
  시계열 — S1 조직 진단의 핵심 대시보드 재료.

### E4. 규모 확장 (인구·공간)

- **인구**: 관계 행렬 O(N²) — 11명 55쌍 → 30명 435쌍 → 50명 1,225쌍. JSON 직렬화가
  20명+에서 병목(탐색 확인) → relationships만 SQLite 이관(다른 저장은 유지, 침습 최소).
  encounter 선택은 이미 우선순위 정렬로 자동 제한되므로 LLM 비용은 인구에 선형이 아니라
  **틱당 encounter 수에 비례** — 인구 확장의 GPU 비용이 완만함(중요한 단위경제 특성).
- **희소 관계 그래프**: 전원-전원 관계 대신 salience 하위 쌍은 휴면 처리(decay만, 저장 생략)
  → 50명 이상에서도 활성 쌍 수를 상수 근처로 유지.
- **멀티 커뮤니티**: 세계 간 캐릭터 이주/소문 전파는 흥미롭지만 A트랙 요구가 아님 — 백로그.

### E5. 멀티테넌트 운영 계층

dir-scoped 락 + 환경변수 격리(HARMONICITY_DATA_DIR/API_URL)까지 완료 상태. 남은 것:
- **테넌트 매니저**: 세계 생성/기동/정지/백업을 프로세스 스폰으로 관리하는 단일 데몬
  (concurrency/run_concurrency.py의 Popen 스윕 코드가 사실상 프로토타입).
- **모델 계층화**: 독백/회고는 소형 모델, 대화/appraisal은 26B — throughput 포화점(N≈4 슬롯)을
  뒤로 미는 가장 싼 방법. llm.py chat()에 용도별 모델 라우팅 파라미터 1개 추가로 가능.
- **용량 계획 실측치**: 1대 5090 = 실시간 12세계. 비실시간(fast 모드) 배치 실험은 시간 분할로
  사실상 무제한. 클라우드 환산은 export_concurrency.py에 이미 존재.

### E6. 도메인 팩 체계화 (확장 속도의 지렛대)

5파일 수동 교체 → **선언적 도메인 팩**(캐릭터/장소/프롬프트/이벤트/예산을 하나의 팩 디렉토리 +
manifest)으로 규격화하고, 팩 검증 스위트(mock 48틱 스모크 + 메트릭 sanity)를 자동화.
- 효과: 새 도메인(예: 특정 고객사 조직) 제작이 "엔지니어링"에서 "저작"으로 바뀜 —
  S1/S2 영업에서 고객별 커스텀 세계를 며칠 단위로 납품 가능.
- 후속: 조직도/설문 데이터 → 캐릭터 정의 자동 초안 생성기(LLM 이용). S1 온보딩 비용을 좌우.

## 2. 응용 서비스 설계 (엔진 위에 세우는 것 — A트랙 정합 순)

### S1. 조직 다이내믹스 시뮬레이터 — 기업 HR/OD (사업 1순위 유지)

- **제공 가치**: "조직개편/정책/신규 채용이 팀 관계·긴장·고립에 만드는 **변화 추이**를
  실행 전에 관찰한다." 예측 점술이 아니라 시나리오 탐색 도구로 포지셔닝(정직성 = 학술 기반 차별화).
- **사용 흐름**: 조직 데이터 → 도메인 팩 생성(E6) → baseline 세계 가동 → 개입 시나리오를
  A/B 실험(E2)으로 실행 → 효과 리포트 + 네트워크 건강 대시보드(E3)
- **필요 확장**: E1(대시보드/API) + E2(핵심) + E6(온보딩) + E3(진단 지표)
- **차별화**: 재현성 — "같은 시나리오를 다시 돌리면 같은 결과"는 컨설팅 리포트가 흉내 못 내는 속성.

### S2. 계산사회과학 연구 플랫폼 — B2B 학술 SaaS (A트랙 확정 축)

- **제공 가치**: 가설 → 세계 설계 → N시드 통제 실험 → mean±std+95%CI → REPRODUCE.md까지
  **논문 파이프라인 전체**. 재현성 ①~④가 그대로 제품 기능표가 됨 (경쟁 사회 시뮬 연구 도구 대비
  record/replay 비트단위 재현은 실측 확보된 희소 역량).
- **사용 흐름**: 연구자가 도메인 팩 저작(E6) → 실험 설계(E2) → API로 데이터 회수(E1) →
  export(기존 ④). 학과 PoC(W3W4 합의된 프로토콜)가 첫 레퍼런스.
- **필요 확장**: E2(핵심) + E1 + E6. E4는 연구 주제에 따라(대규모 사회 실험 요구 시).
- **가격 근거**: 세계당 GPU 월 ~1시간 실측 → 원가 대비 마진 구조를 venture-studio가 설계 가능.

### S3. 교육 시민 시뮬레이션 (A트랙 확정 축, 서사 품질 최고 실측)

- **제공 가치**: 학생이 정책/사건을 설계해 마을에 주입하고, 사람들이 **어떻게 변해가는지**를
  관찰·토론 (벤치마크에서 교육 도메인이 서사 밀도 최고). 승패 없는 관찰형 — 게임 제외 원칙과 충돌 없음.
- **사용 흐름**: 교사가 시나리오 팩 선택 → 수업 중 실시간 관전(E1 SSE 피드) → 학생 개입 제출
  (`POST /events`) → 다음 수업에서 변화 추이 비교(E2 간이판)
- **필요 확장**: E1(핵심 — 관전 UI) + E3(서사 연속성이 몰입 좌우) + E5(반별 세계 = 멀티테넌트,
  N≤12 실측이 "한 학년 동시 수업" 용량 근거)

### S4. 합성 사회 데이터 서비스 (파생 — 한계비용 ~0)

- **제공 가치**: 관계 맥락이 일관된 **합성 대화 코퍼스 + 관계/평판/욕구 시계열** —
  LLM 파인튜닝(페르소나 일관성, 멀티턴 관계 유지), 에이전트 평가, 사회과학 방법론 테스트용.
- 근거: record 모드가 모든 LLM 입출력을 이미 jsonl로 적재. 24틱 193호출 재현 검증 완료 —
  데이터에 재현 매니페스트를 붙여 팔 수 있음("이 데이터셋은 seed로 재생성 가능").
- **필요 확장**: 사실상 0 — 라이선스/익명화 정책만 (venture-studio 사안). fast 모드 배치 생산.

### S5. 페르소나 패널 / 가상 FGD — 소비자 MarTech (3순위 유지, 보류 권장)

- consumer 도메인 자산은 있으나 벤치마크 결론(차별화 약점) 그대로 — E1/E2 완성 후
  S1 영업의 부가 옵션("신제품 정책을 조직+고객 페르소나 양쪽에 시뮬")으로만 편입 권장.

## 3. 다른 서비스에 제공할 수 있는 가치 (엔진 통째가 아닌 부품 단위)

하모니시티를 수직 서비스(2장)로만 보지 않고, 검증된 서브시스템을 **수평 컴포넌트**로 노출:

| 컴포넌트 | 내용 | 수요처 예시 |
|----------|------|------------|
| **V1. 관계 엔진 레이어** | 4축 관계 상태기계 + 항상성(감쇠/soft ceiling/포화 방지 — P2로 장기 안정성 실증) | 캐릭터 챗/컴패니언 서비스: "관계가 기억되고 변하되 포화·붕괴하지 않는" 레이어. Leo 생태계 내 jamnai/lotti류 캐릭터 프로젝트에 즉시 적용 가능 |
| **V2. Appraisal API** | 임의 대화 로그 → OCC 기반 구조화 JSON(관계Δ/욕구Δ/신념/소문). engine/appraisal.py 단독 절출 | 챗봇 감정 분석, CS 대화 품질 모니터링, 에이전트 파이프라인의 감정 상태 추적 |
| **V3. 평판·정보전파 모듈** | 관찰자별 독립 평판 행렬 + 소문 truth_value 감쇠 전파 | 멀티에이전트 시스템(agent-comm 생태계 포함)의 신뢰/평판 계층, 정보전파 연구 |
| **V4. 재현성 하네스** | seed_everything + LLM record/replay + multiseed 통계 + export — LLM 파이프라인 범용 | oven 내 다른 LLM 프로젝트의 회귀 테스트/A/B 평가, 타 에이전트의 LLM 실험 재현 인프라 |
| **V5. LLM 사회성 벤치마크** | 동일 세계·동일 seed에서 LLM만 교체 → 관계 메트릭 분산·대화 품질 비교 (eval_llm_compare 계보) | 모델 선정 평가(oven 자체 수요: Gemma vs 후속 모델 판단), 외부에는 "사회 시뮬 기반 LLM 벤치" 리포트 |

- V1/V2가 절출 비용 대비 수요 접점이 가장 넓음. V4는 oven 내부에서 이미 재사용 중(사실상 검증 완료).

## 5. 단계별 로드맵 (기술 관점 제안 — 일정 확정은 Leo 결재)

- **Phase A (관문)**: E1 관측 API(read-only 먼저) + E2 `orchestrate_ab` — 기존 코드 재사용률이
  높아 둘 다 단기(각 수일~1주 스케일, 재현성 트랙 실적 기준). 완료 시 S2 학과 PoC에 바로 투입 가능.
- **Phase B (제품화 재료)**: E1 개입 API + E6 도메인 팩 규격 + E3 L2.5 요약 기억.
  완료 시 S1 파일럿 데모 가능.
- **Phase C (규모)**: E5 테넌트 매니저 + 모델 계층화, E4 SQLite 이관 (첫 B2B 본계약 트리거 —
  기존 Leo 결정 "격리 트랙은 본계약 트리거" 원칙 연장).
- **상시**: S4 데이터 파이프라인은 Phase와 독립적으로 fast 배치 생산 가능 (GPU 유휴 슬롯 활용).

**리스크**
1. **단일 GPU 의존**: ogo 5090 1대 + 네트워크 불안정(USB WiFi 이슈) — 상용 SLA 불가.
   파일럿까지는 충분, 본계약 시 클라우드 환산치(export_concurrency)로 인프라 계획 필요.
2. **모델 의존성**: 서사 품질이 Gemma-4-26B에 결박. V5 벤치마크가 모델 교체 리스크의 보험.
3. **⑤배치불변 미해결**: 로그 없는 상태의 완전 결정성은 여전히 R&D — 단 record/replay 우회로
   제품 요구는 충족(기존 결론 유지). 학술 커뮤니케이션에서 한계 명시 지속.
